# #11 Completion Check

`iterm2/herdr.json` に `Link Color` / `Selected Text Color` / `Use Selected Text Color` /
`Use Separate Colors for Light and Dark Mode` を追加した。
残りの未定義キー(`Cursor Guide Color` `Match Background Color` `Underline Color` `Tab Color` ほか)は
**描画されないか、iTerm2 が描画先から文字色を自分で決めるため定義しない**と判断した。根拠は下記。

出典は iTerm2 3.6.11(手元の `/Applications/iTerm.app` の `CFBundleShortVersionString`)ではなく
**master のソース**を読んでいる(3.6.11 のタグ済みソースは配布されていない)。この差は下の「未確認」に記す。
ソースは `https://raw.githubusercontent.com/gnachman/iTerm2/master/<path>` から取得。

## 基準に対して未達のまま残るもの / 申し送り

- **`Badge Color` `#fb4934` は `Background Color` `#282828` に対して 4.29:1** で 4.5 に届かない。今回は変更していない。理由は3つ: (1) 完了基準2が名指しする3組(太字・カーソル文字・選択文字)に含まれない、(2) バッジは巨大な透かし文字で、WCAG の large text 基準 3:1 は満たす、(3) `Badge Format` が両プロファイルとも不在 → 既定 `@""`(`iTermProfilePreferences.m:961`)なので**現状バッジは1文字も描画されない**。Gruvbox のパレットに 4.5:1 を満たす赤は無く(`red #cc241d` はさらに低い)、赤以外にするとバッジの警告色という意味が壊れる。基準を字義どおり全色に当てるならここは要判断なのでコーディネータに委ねる
- **リンクが選択範囲の中にあるとき、`Link Color` が `Selection Color` の上に載る**。`iTermTextDrawingHelperGetTextColor()` の分岐順が `isMatch` → `inUnderlinedRange` → `hasSelectedText` なので、リンク色が選択文字色より優先される。`Selection Color` が `#ffffff` に固定されている以上、**この組み合わせで 4.5:1 を満たす `Link Color` は数学的に存在しない**: `#ffffff` に対して 4.5:1 を満たすには相対輝度 ≤ 0.1833、`#282828` に対して満たすには ≥ 0.2705 が必要で両立しない。主用途(端末背景の上のリンク)を最大化する値を選び、この残差は記録にとどめた
- **`Use Separate Colors for Light and Dark Mode` についての当初の判断は誤りだったので訂正した。** 「true に倒れてもサフィックス付きキー群は内部で整合しており可読性は保たれる」と書いていたが、実測値を当てると成り立たない: `Cursor Text Color (Dark)` `#ffffff` を `Cursor Color (Dark)` `#bbbbbb` の上に載せると **1.92:1** で、完了基準2が名指しする「カーソル文字」がそのまま基準割れになる。`Ansi 4 Color (Dark)` `#0000bb` / 背景 `#000000` も 1.72:1。よって `false` を明示的に固定した
- **master には保険があるが、それに寄りかからない判断をした。** `shouldDisableSeparateColorsForDynamicProfile:prototype:` は「DP がフラグ未指定 / 親が真 / DP に非サフィックス色キーがある / DP にサフィックス付きキーが無い」の4条件が揃うとき merged 側で `@NO` に倒す。今の `herdr.json` はこの4条件を満たすので、master のバイナリなら明示しなくても救われる。それでも固定した理由は2つ: (a) 読んでいるのは master であって手元の 3.6.11 ではなく、この保険がその版に入っているかを確かめられていない、(b) 保険は条件4で壊れる — 将来 `herdr.json` に `(Dark)` 付きキーを1つでも足した瞬間、親の true がそのまま効いて 22 色が迂回される。明示すれば条件1で確定し、どちらの穴も塞がる
- `Use Bright Bold`(= `Use Bold Color`)は引き続き Default から継承している。false に倒れても太字は `Foreground Color` に落ちるだけで色は同じ `#ebdbb2`(10.75:1 のまま)で、**可読性の基準を破らない**ので固定しなかった

## 未確認

- **実機での確認をしていない**。配置先(`~/Library/Application Support/iTerm2/DynamicProfiles/herdr.json`)は現在 repo の版とバイト一致だが、配置は #8 の担当なので今回は書き換えていない。したがって「新しい3キーが iTerm2 に読み込まれて `New Bookmarks` に反映される」ことと、実際の描画(選択・リンク)の見た目は未確認。`setup.sh` を流したあとに `plutil` で `Selected Text Color` = `#282828` / `Link Color` = `#83a598` / `Use Selected Text Color` = `True` / `Use Separate Colors for Light and Dark Mode` = `False` を確認するのが検証手順
- **読んだソースは master であって 3.6.11 のタグではない**。3.6.11 のソースは配布されておらず、差分を突き合わせられていない。既定値表(`defaultValueMap`)と分岐(`Use *` フラグ、`TextColorForMatch`)は長期に安定している箇所だが、この機械で動いているバイナリそのもので確かめたわけではない
- **Metal レンダラの経路は読んでいない**。上記は `iTermTextDrawingHelper` / `iTermAttributedStringBuilder`(CoreGraphics 経路)。文字色の決定は `iTermAttributedStringBuilder` に集約されており Metal 経路も同じビルダを使う造りに見えるが、確認はしていない
